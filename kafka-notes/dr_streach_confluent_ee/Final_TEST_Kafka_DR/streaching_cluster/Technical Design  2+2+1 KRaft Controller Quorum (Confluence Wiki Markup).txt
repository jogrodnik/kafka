h1. Technical Design: 2+2+1 KRaft Controller Quorum
h2. DC1 Hong Kong + DC2 Hong Kong + GKE asia-east2

*Status:* Revised technical design (v2 — corrected and verified against Confluent Platform 8.3 / Apache Kafka 4.3 official documentation; expanded with custom Docker image and Helm chart detail)
*Scope:* Confluent Platform *8.3.0* / Apache Kafka *4.3.x* KRaft control plane
*Deployment model:* Custom container image + custom Helm chart (StatefulSet-based); no Confluent for Kubernetes (CFK)
*GKE role:* One controller-only KRaft voter; no Kafka broker and no Kafka data plane

----

h2. 1. Purpose and Design Goal

The target is a five-voter KRaft controller quorum distributed across three independent infrastructure locations:

||Site||Role||KRaft voters||Kafka brokers||
|DC1 Hong Kong|Full Kafka site|2|Yes|
|DC2 Hong Kong|Full Kafka site|2|Yes|
|GKE {{asia-east2}} Hong Kong|Controller-only site ("0.5 DC")|1|No|

Total KRaft voters: *5*.
Required majority: *3*.

The purpose of the GKE site is only to preserve the KRaft majority after complete loss of either DC1 or DC2.

This document covers the *Kafka/KRaft control plane only*. Broker topic-replication design, RF, {{min.insync.replicas}}, ISR/ELR, producer acknowledgements, and application DR are separate data-plane topics.

Confluent Platform 8.3 bundles Apache Kafka 4.3 — this is stated explicitly in the Confluent Platform 8.3 release notes ("Confluent Platform 8.3 includes Kafka 4.3") [Confluent Platform 8.3 Release Notes|https://docs.confluent.io/platform/current/release-notes/index.html]. The interoperability table confirms the same *8.3.x ↔ 4.3.x* family mapping [Supported Versions and Interoperability|https://docs.confluent.io/platform/current/installation/versions-interoperability.html]. *Gap:* neither page publishes the exact Apache Kafka patch version paired specifically with Confluent Platform *8.3.0* (only the family-level 8.3.x ↔ 4.3.x mapping is documented) — confirm the exact bundled patch with {{kafka-features.sh describe}} (Section 4) at deployment time rather than assuming it from this table alone.

h2. 2. Quorum Topology

Recommended controller identities:

{code}
DC1:
  C101
  C102

DC2:
  C201
  C202

GKE asia-east2:
  C301
{code}

Logical quorum:

{code}
                5-voter KRaft quorum

          DC1                     DC2
      +-----------+           +-----------+
      | C101      |           | C201      |
      | C102      |           | C202      |
      +-----+-----+           +-----+-----+
            \                       /
             \                     /
              \                   /
               +------ C301 ------+
                   GKE asia-east2
{code}

Quorum majority:

{code}
N = 5
majority = floor(N / 2) + 1 = 3
{code}

The fifth GKE node is a *normal KRaft voter*, not a special witness protocol role. It stores and replicates the KRaft metadata log and participates in elections.

----

h2. 3. Failure Behaviour

||Failure||Controllers remaining||Result||
|No failure|5/5|Quorum available|
|One controller fails|4/5|Quorum available|
|GKE/C301 fails|4/5|Quorum available|
|Entire DC1 fails|C201 + C202 + C301 = 3/5|Quorum available|
|Entire DC2 fails|C101 + C102 + C301 = 3/5|Quorum available|
|DC1 + GKE fail|2/5|Quorum lost|
|DC2 + GKE fail|2/5|Quorum lost|
|Any 3 voters are mutually connected|3/5|Quorum can operate|
|Network partition leaves only 2 mutually connected voters|2/5|No leader can be elected|

The key improvement over the earlier 3+2 two-DC design is:

{code}
old:
DC1 = 3
DC2 = 2

loss DC1 -> 2/5 -> quorum lost

new:
DC1 = 2
DC2 = 2
GKE = 1

loss DC1 -> 3/5 -> quorum survives
loss DC2 -> 3/5 -> quorum survives
{code}

Normal single-site failure therefore must *not* require {{force-standalone}} or manual quorum reconstruction.

h2. 4. Kafka / KRaft Version Model

Target platform:

{code}
Confluent Platform 8.3.0
Apache Kafka 4.3.x (bundled by CP 8.3; exact patch pairing for 8.3.0 specifically not published — verify per-deployment, see Section 1 gap note)
Java 21 recommended for Confluent Platform 8.3.x; Java 17 and Java 25 also supported; Eclipse Temurin is a supported distribution
{code}

Source: [Supported Versions and Interoperability|https://docs.confluent.io/platform/current/installation/versions-interoperability.html] (Java version table); [Confluent Platform 8.3 Release Notes|https://docs.confluent.io/platform/current/release-notes/index.html] (Kafka 4.3 bundling).

For Confluent Platform 8.3.x, use the dynamic KRaft quorum model.

Required feature:

{code}
kraft.version = 1
{code}

{{kraft.version = 1}} (dynamic controller cluster support) was introduced in Apache Kafka 4.1 [Apache Kafka — KRaft|https://kafka.apache.org/43/operations/kraft/]. Dynamic controllers are supported by Confluent Platform starting with *7.9.x*, but a cluster must either be bootstrapped for dynamic controllers or explicitly upgraded via {{kafka-features.sh}} — see the compatibility table below [Supported Versions and Interoperability|https://docs.confluent.io/platform/current/installation/versions-interoperability.html]:

||Confluent Platform version||Dynamic controllers||Static controllers||
|7.2.x and earlier|Not compatible|Not compatible|
|7.3.x–7.8.x|Not compatible|Compatible|
|7.9.x and later|Compatible|Compatible|

Verify:

{code:language=bash}
kafka-features.sh \
  --bootstrap-controller c101.kafka.internal:9093 \
  describe
{code}

Expected:

{code}
Feature: kraft.version
FinalizedVersionLevel: 1
{code}

(A {{FinalizedVersionLevel}} of {{0}}, or the field being absent, indicates a static quorum; {{1}} or above indicates dynamic — [Apache Kafka — KRaft|https://kafka.apache.org/43/operations/kraft/].)

For a dynamic controller quorum:

{code:language=properties}
controller.quorum.bootstrap.servers=c101.kafka.internal:9093,c102.kafka.internal:9093,c201.kafka.internal:9093,c202.kafka.internal:9093,c301.kafka.internal:9093
{code}

Do *not* configure:

{code:language=properties}
controller.quorum.voters=...
{code}

after the cluster has been converted/formatted for dynamic quorum.

{{controller.quorum.bootstrap.servers}} is a discovery seed list. It does not define the authoritative current voter membership; membership is stored in the KRaft metadata state.

*Auto-join capability (Confluent Platform 8.2+, applies to 8.3.0):* on Confluent Platform 8.2 and later, a newly formatted controller with {{controller.quorum.auto.join.enable=true}} joins a running dynamic quorum automatically after startup, without a separate manual {{add-controller}} step. On earlier releases the new controller must always be added explicitly via {{kafka-metadata-quorum.sh add-controller}} [Configure and Monitor KRaft|https://docs.confluent.io/platform/current/kafka-metadata/config-kraft.html]. Section 13 and Section 14 give both the automatic and the manual procedure; choose one deliberately as an operational/change-control decision rather than mixing them.

h2. 5. Network Architecture

h3. 5.1 Required reachability

Every controller must be able to establish TCP connectivity to every other controller endpoint.

Required logical mesh:

{code}
C101 <-> C102
C101 <-> C201
C101 <-> C202
C101 <-> C301

C102 <-> C201
C102 <-> C202
C102 <-> C301

C201 <-> C202
C201 <-> C301

C202 <-> C301
{code}

Broker nodes in DC1 and DC2 must also be able to reach sufficient controller bootstrap endpoints.

The controller listener port is a deployment choice. Example used in this design:

{code}
TCP 9093
{code}

There is no Kafka requirement that the port be {{9074}}; use the same explicit controller listener port consistently in Helm, firewall policy, DNS and TLS configuration.

h3. 5.2 Private routing

Required design:

{code}
DC1 <------ private routed network ------> DC2
 |                                      |
 |                                      |
 +------- private connectivity ---------+
                 to GCP
                  |
             Cloud Router
                  |
              GKE VPC
                  |
                C301
{code}

Production traffic between the on-premises DCs and GKE should use dedicated/private hybrid connectivity such as Cloud Interconnect or an equivalent private WAN path [Google Cloud — Cloud Interconnect|https://cloud.google.com/network-connectivity/docs/interconnect].

Avoid putting KRaft controller communication over the public Internet.

BGP and route propagation must provide bidirectional reachability between:

{code}
DC1 controller subnet
DC2 controller subnet
GKE node / service endpoint subnet used by C301
{code}

Avoid overlapping CIDRs across the three environments.

----

h2. 6. Latency, Jitter and Packet Loss

Confluent's multi-region guidance treats stable, low-latency connectivity as a prerequisite and identifies approximately 100 ms as a practical upper boundary for stretched-cluster designs.

For this Hong Kong / Hong Kong / GCP Hong Kong architecture, the engineering target should be much tighter:

||Path||Recommended engineering target||
|DC1 ↔ DC2 RTT average|< 10 ms|
|DC1 ↔ C301 RTT average|< 10–15 ms|
|DC2 ↔ C301 RTT average|< 10–15 ms|
|p95|< 20 ms|
|p99|< 25–30 ms|
|Packet loss under normal operation|effectively 0%; target < 0.01%|
|Sustained packet loss|unacceptable|
|Long latency spikes / route flapping|unacceptable|

These are *design targets*, not Kafka protocol hard limits.

For KRaft, stable tail latency is more important than a low average with large spikes.

----

h2. 7. Bandwidth

C301 carries no Kafka topic partitions.

Traffic to the GKE site consists primarily of:

{code}
KRaft heartbeats
Raft fetch/replication
__cluster_metadata-0 records
metadata snapshots / controller catch-up
administrative controller traffic
TLS overhead
monitoring
{code}

Therefore bandwidth requirements for the GKE leg are normally low compared with broker replication.

DC1 ↔ DC2 is different because that path may also carry broker replica traffic and must be sized independently from the KRaft control-plane requirement.

h2. 8. GKE Controller Design

h3. 8.1 Location

Use:

{code}
GCP region: asia-east2
Location: Hong Kong
{code}

h3. 8.2 Workload

Run exactly one Kafka process with:

{code:language=properties}
process.roles=controller
node.id=301
{code}

Do not run on C301:

{code}
broker role
Kafka topic replicas
Schema Registry
Kafka Connect
ksqlDB
Control Center
application workloads
{code}

h3. 8.3 Kubernetes deployment

Use a StatefulSet managed by the existing custom Helm deployment model.

Example:

{code:language=yaml}
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: kraft-controller-gke
spec:
  replicas: 1
  serviceName: kraft-controller-gke
  selector:
    matchLabels:
      app: kraft-controller-gke
  template:
    metadata:
      labels:
        app: kraft-controller-gke
    spec:
      terminationGracePeriodSeconds: 120
      containers:
        - name: controller
          image: internal-registry/kafka-controller:8.3.0
          volumeMounts:
            - name: metadata
              mountPath: /var/lib/kafka/metadata
  volumeClaimTemplates:
    - metadata:
        name: metadata
      spec:
        accessModes:
          - ReadWriteOnce
        storageClassName: premium-rwo
        resources:
          requests:
            storage: 20Gi
{code}

The exact disk size must be selected from observed metadata growth and retention requirements.

h3. 8.4 Compute and availability

C301 does not need broker-scale compute.

Use non-Spot compute. Do not place the only third-site voter on Spot/Preemptible nodes.

Prefer a regional GKE control plane with non-Spot capacity available in more than one zone. C301 remains one Kafka voter; Kubernetes HA is only used to restart that voter after infrastructure failure.

Do not run two simultaneous C301 replicas with the same {{node.id}} and metadata directory.

h3. 8.5 Custom Docker Image

Since this design uses a self-built container image rather than Confluent for Kubernetes, the image must be built and version-pinned explicitly, and must contain the idempotent-startup logic required by Section 9.

{code:language=dockerfile}
FROM eclipse-temurin:21-jre-jammy AS base

ARG CONFLUENT_VERSION=8.3.0
ENV CONFLUENT_VERSION=${CONFLUENT_VERSION}

# Confluent Platform 8.3.0 binaries pulled from the approved internal artifact mirror,
# not from a public Confluent base image, to retain full control over the OS layer.
COPY confluent-${CONFLUENT_VERSION} /opt/confluent
COPY entrypoint-controller.sh /opt/confluent/bin/entrypoint-controller.sh

RUN useradd --system --uid 10001 --home /opt/confluent kafka \
    && chown -R kafka:kafka /opt/confluent \
    && chmod +x /opt/confluent/bin/entrypoint-controller.sh

USER kafka
WORKDIR /opt/confluent
ENTRYPOINT ["/opt/confluent/bin/entrypoint-controller.sh"]
{code}

Java base image note: Confluent Platform 8.3.x supports Java 17, 21 and 25, with *21 recommended*; Eclipse Temurin is an explicitly supported JDK distribution [Supported Versions and Interoperability|https://docs.confluent.io/platform/current/installation/versions-interoperability.html].

Entrypoint responsibilities — this is the mechanism that satisfies the Section 9 requirement to never reformat an existing metadata directory on Pod restart, and implements the format/join sequence from Section 4/14:

{code:language=bash}
#!/usr/bin/env bash
set -euo pipefail

METADATA_DIR="/var/lib/kafka/metadata"
CONFIG_FILE="/etc/kafka/controller.properties"

if [ ! -f "${METADATA_DIR}/meta.properties" ]; then
  echo "No existing meta.properties found - formatting new controller storage to join existing quorum"
  kafka-storage.sh format \
    --cluster-id "${CLUSTER_ID}" \
    --no-initial-controllers \
    --config "${CONFIG_FILE}"
else
  echo "Existing meta.properties found - skipping format, starting controller with existing identity"
fi

exec kafka-server-start.sh "${CONFIG_FILE}"
{code}

{{--no-initial-controllers}} is the documented flag for formatting a node that should join an existing dynamic quorum rather than create a new one [Configure and Monitor KRaft|https://docs.confluent.io/platform/current/kafka-metadata/config-kraft.html] [Apache Kafka — KRaft|https://kafka.apache.org/43/operations/kraft/].

Image tag policy: pin the exact patch, e.g. {{internal-registry/kafka-controller:8.3.0}}; never use a floating tag such as {{8.3}} or {{latest}} for a KRaft controller image — a silent patch upgrade across a quorum can introduce version skew (Section 17, Version consistency).

h3. 8.6 Helm Chart Structure

The controller StatefulSet in Section 8.3 is templated from one shared Helm chart, parameterised per site so the same chart deploys DC1, DC2 and GKE controllers without duplicated logic. Representative {{values.yaml}} fragment for the GKE site:

{code:language=yaml}
site:
  name: gke-asia-east2
  role: controller-only

image:
  repository: internal-registry/kafka-controller
  tag: "8.3.0"
  pullPolicy: IfNotPresent

controller:
  nodeId: 301
  clusterId: "<EXISTING_CLUSTER_ID>"
  quorumBootstrapServers:
    - c101.kafka.internal:9093
    - c102.kafka.internal:9093
    - c201.kafka.internal:9093
    - c202.kafka.internal:9093
    - c301.kafka.internal:9093
  autoJoinEnabled: true

persistence:
  storageClassName: premium-rwo
  size: 20Gi

nodeSelector:
  cloud.google.com/gke-nodepool: kraft-controller-pool

tolerations:
  - key: dedicated
    operator: Equal
    value: kraft-controller
    effect: NoSchedule

podDisruptionBudget:
  enabled: true
  maxUnavailable: 0

tls:
  secretName: kraft-controller-tls
  caSecretName: kraft-ca-bundle
{code}

The same chart, deployed with {{site.name=dc1}}/{{dc2}}, {{controller.nodeId}} set per host, and {{persistence.storageClassName}} pointed at the on-premises CSI driver, produces the DC1/DC2 controllers. {{podDisruptionBudget.maxUnavailable: 0}} on the single-replica GKE StatefulSet prevents a voluntary eviction (for example a GKE node-pool upgrade) from removing the only Site 0.5 voter without an explicit manual override.

h2. 9. Persistent Metadata Storage

C301 must use persistent block storage for the KRaft metadata directory.

Recommended GKE CSI class:

{code}
premium-rwo
{code}

which is documented by Google Cloud as backed by SSD Persistent Disk, versus {{standard-rwo}} which is backed by balanced Persistent Disk [Using SSD Persistent Disks|https://docs.cloud.google.com/kubernetes-engine/docs/how-to/persistent-volumes/ssd-pd] [Persistent Disk CSI Driver|https://cloud.google.com/kubernetes-engine/docs/how-to/persistent-volumes/gce-pd-csi-driver]. *Gap:* Google's documentation does not publish the exact underlying {{type:}} parameter (e.g. {{pd-ssd}} vs {{pd-balanced}}) for the built-in {{premium-rwo}} class name — if the exact disk type matters for capacity/IOPS planning, provision a custom {{StorageClass}} with an explicit {{type: pd-ssd}} parameter instead of relying on the built-in class.

A zonal Persistent Disk survives Pod and node restart but remains tied to its zone. If recovery after a zone failure is required, evaluate Regional Persistent Disk or an equivalent multi-zone persistence design.

Required properties:

{code}
PVC survives Pod recreation
PVC is not automatically deleted during normal StatefulSet operations
single writer only
filesystem ownership remains stable
metadata directory is not reformatted on every Pod start
{code}

The startup script must distinguish an empty metadata volume from an already-formatted KRaft metadata volume (implemented in Section 8.5).

Never run unconditional {{kafka-storage.sh format}} on Pod startup.

h2. 10. Stable Network Identity and DNS

Do not use an ephemeral Pod IP as the long-term identity of C301.

Define a stable private DNS endpoint, for example:

{code}
c301.kafka.internal
{code}

All controllers and brokers must resolve the controller names consistently:

{code}
c101.kafka.internal
c102.kafka.internal
c201.kafka.internal
c202.kafka.internal
c301.kafka.internal
{code}

The GKE endpoint must remain private and reachable through the routed hybrid network.

Preserve one-to-one identity:

{code}
c301.kafka.internal -> C301 only
{code}

Do not use a single virtual address that load-balances Raft peer connections across different controller IDs.

h2. 11. TLS and Firewalling

Controller-to-controller communication should use TLS.

Example:

{code:language=properties}
process.roles=controller
node.id=301
controller.listener.names=CONTROLLER
listeners=CONTROLLER://0.0.0.0:9093
listener.security.protocol.map=CONTROLLER:SSL
{code}

The certificate presented by C301 must match the stable endpoint, for example:

{code}
SAN: DNS:c301.kafka.internal
{code}

The same CA trust model must be available in DC1, DC2 and GKE.

Firewall rules should allow only required controller and broker source networks to the controller listener.

Do not expose the controller listener publicly.

h2. 12. MTU and TCP Path Validation

Verify path MTU end-to-end from real controller hosts/pods.

Test all paths:

{code}
DC1 -> DC2
DC1 -> C301
DC2 -> C301
C301 -> DC1
C301 -> DC2
{code}

Avoid fragmentation and PMTU black holes.

Validate TCP reachability against the real controller listener and test long-lived connections, not only ICMP ping.

h2. 13. C301 Controller Configuration

Example controller-only configuration, using the Confluent Platform 8.2+ auto-join capability (Section 4) as the primary path:

{code:language=properties}
process.roles=controller
node.id=301

controller.listener.names=CONTROLLER
listeners=CONTROLLER://0.0.0.0:9093
listener.security.protocol.map=CONTROLLER:SSL

controller.quorum.bootstrap.servers=c101.kafka.internal:9093,c102.kafka.internal:9093,c201.kafka.internal:9093,c202.kafka.internal:9093,c301.kafka.internal:9093

metadata.log.dir=/var/lib/kafka/metadata
{code}

If organizational change control requires an explicit, auditable step instead of automatic joining, omit {{controller.quorum.auto.join.enable}} (defaults to disabled) and follow the manual procedure in Section 14.3.

Important:

{code}
controller.quorum.bootstrap.servers != voter membership
{code}

The current voter set is maintained by KRaft metadata.

h2. 14. Adding C301 to an Existing Dynamic Quorum

For an existing healthy dynamic quorum, add C301 using either the automatic join path (Confluent Platform 8.2+, recommended default for this design) or the manual {{add-controller}} path (explicit change control, required on releases before 8.2).

h3. 14.1 Format new C301 storage

Use the existing Kafka cluster ID:

{code:language=bash}
kafka-storage.sh format \
  --cluster-id <EXISTING_CLUSTER_ID> \
  --no-initial-controllers \
  --config /etc/kafka/controller.properties
{code}

Do not use {{--standalone}} when adding C301 to an existing quorum — {{--standalone}} bootstraps a controller as the sole initial voter of a *new* quorum, which is not this scenario [Configure and Monitor KRaft|https://docs.confluent.io/platform/current/kafka-metadata/config-kraft.html].

h3. 14.2 Automatic join (Confluent Platform 8.2+, recommended)

If {{controller.quorum.auto.join.enable=true}} is set in C301's configuration (Section 13), starting C301 after the format step in 14.1 is sufficient — it will discover the quorum through {{controller.quorum.bootstrap.servers}} and join automatically, with no separate {{add-controller}} command required [Configure and Monitor KRaft|https://docs.confluent.io/platform/current/kafka-metadata/config-kraft.html]. Confirm the result with the verification steps in 14.4.

h3. 14.3 Manual join via add-controller (fallback / pre-8.2 / explicit change control)

Start C301 (with {{controller.quorum.auto.join.enable}} unset or {{false}}) and allow it to catch up with the current metadata log before promoting it, then run {{add-controller}} using *C301's own controller configuration file* as {{--command-config}}, bootstrapped against any existing healthy controller:

{code:language=bash}
kafka-metadata-quorum.sh \
  --command-config /etc/kafka/controller.properties \
  --bootstrap-controller c101.kafka.internal:9093 \
  add-controller
{code}

{{--command-config}} must point at the *new controller's own* properties file (containing its identity, directory ID and any TLS/auth settings), not a generic admin config — the tool derives the joining controller's identity from it; {{--bootstrap-controller}} points at any existing quorum member used only to reach the cluster [Configure and Monitor KRaft|https://docs.confluent.io/platform/current/kafka-metadata/config-kraft.html] [Apache Kafka — KRaft|https://kafka.apache.org/43/operations/kraft/].

*Note on tooling evolution:* a proposed simplification (KIP-1141) would allow {{add-controller --controller-id <id>}} against a {{--bootstrap-controller}} endpoint without supplying the new controller's config file. As of this research, KIP-1141 status is *Voting* and is not confirmed present in Apache Kafka 4.3 documentation [KIP-1141|https://cwiki.apache.org/confluence/display/KAFKA/KIP-1141:+Simplifying+MetadataQuorumCommand+by+Leveraging+Admin+API+for+Controller+Management] — do not rely on the shorthand syntax for Confluent Platform 8.3.0; use the {{--command-config}} form above.

h3. 14.4 Verify replication and membership

{code:language=bash}
kafka-metadata-quorum.sh \
  --bootstrap-controller c101.kafka.internal:9093 \
  describe --replication
{code}

Verify that C301 is caught up before relying on it as a voter.

{code:language=bash}
kafka-metadata-quorum.sh \
  --bootstrap-controller c101.kafka.internal:9093 \
  describe --status
{code}

4 followers

h2. 16. Pre-Production Acceptance Tests

||Test||Expected result||
|{{kraft.version}}|{{FinalizedVersionLevel=1}}|
|Normal voter count|5 voters|
|Stop C301|quorum remains 4/5|
|Complete loss of DC1|DC2 + C301 = 3/5; quorum remains available|
|Complete loss of DC2|DC1 + C301 = 3/5; quorum remains available|
|Break DC1↔GKE only|no unexpected quorum loss|
|Break DC2↔GKE only|no unexpected quorum loss|
|Restart C301 Pod|same metadata PVC reused, no reformat|
|Kill node hosting C301|controller recovers according to GKE/storage design|
|DNS validation|all five controller names resolve correctly|
|TLS validation|mutual connectivity and hostname verification succeed|
|RTT/p95/p99|inside agreed engineering limits|
|Packet loss|effectively zero under normal conditions|
|PMTU|no fragmentation/black-hole issue|
|Hybrid path failover|routing converges without prolonged KRaft instability|
|Auto-join path (if enabled)|new/replaced controller joins without manual add-controller|

The mandatory DR tests are complete loss of DC1, complete loss of DC2 and independent loss of C301.

During every test observe leader election, High Watermark, metadata replication lag and time to stable quorum.

h2. 17. Technical Risks

h3. Common-mode network failure

The GKE voter improves quorum resilience only if the path to GKE is sufficiently independent from the infrastructure whose failure can remove DC1 or DC2.

A shared router, firewall, WAN edge, carrier or route reflector can become the real common-mode failure.

h3. GKE zone dependency

A single C301 Pod using a zonal disk can be temporarily unavailable after a zone-level failure. If this overlaps with complete loss of one DC, quorum can fall from 3/5 to 2/5.

h3. DNS dependency

DNS needed for controller endpoints must remain available during DR.

h3. Storage formatting risk

Accidental formatting of an existing metadata directory destroys the local KRaft metadata copy and identity. The entrypoint logic in Section 8.5 is the primary control against this.

h3. Version consistency

Keep controller binaries on the same approved Confluent Platform/Kafka patch level unless Confluent explicitly confirms a mixed build is supported. Enforce this via the pinned image tag policy in Section 8.5 (no floating tags).

h3. Tooling-version risk (new)

Do not adopt not-yet-released command-line simplifications (e.g. KIP-1141's proposed {{add-controller --controller-id}} shorthand, Section 14.3) into runbooks before they are confirmed shipped and documented for the deployed Kafka version.

The architecture is technically strong because complete loss of either DC1 or DC2 leaves a legal KRaft majority without {{force-standalone}} or manual quorum reconstruction.

Production approval should depend on measured DC1↔DC2↔GKE latency, p99 jitter, packet loss, MTU, hybrid-routing failover, DNS, TLS and full-site-loss tests.

h2. 19. Documentation Gaps and Verification Notes

Consistent with the technical rigor required for this design, the following points are explicitly flagged as unconfirmed or inferred, not vendor-guaranteed, and must be re-verified against the live environment before production sign-off:

# The exact Apache Kafka patch version bundled with Confluent Platform *8.3.0* specifically (as opposed to the general 8.3.x family) is not published in Confluent's interoperability table — confirm via {{kafka-features.sh describe}} against the deployed binaries.
# KIP-1141's simplified {{add-controller --controller-id}} syntax (Section 14.3) is in *Voting* status and not confirmed present in Kafka 4.3 — the manual procedure in this document uses only the confirmed {{--command-config}} + {{--bootstrap-controller}} form.
# GKE's {{premium-rwo}} StorageClass is documented as SSD-backed, but Google does not publish the exact underlying {{type:}} parameter for the built-in class name — use a custom {{StorageClass}} with an explicit {{type: pd-ssd}} if the precise disk type must be guaranteed.
# No Confluent, CFK, or Apache Kafka source specifies a minimum Kubernetes control-plane footprint for a controller-only site; the regional-control-plane recommendation in Section 8.4 is this design's own choice, not a vendor requirement.
# The Dockerfile and Helm chart in Sections 8.5–8.6 are this project's own implementation pattern (no CFK used); they are illustrative of the required behavior (pinned version, idempotent format-on-first-boot, non-root user, PDB protection) rather than a vendor-published reference architecture.
